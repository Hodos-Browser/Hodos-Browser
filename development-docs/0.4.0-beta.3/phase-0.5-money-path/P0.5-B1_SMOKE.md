# P0.5-B1 — live T3 approval smoke (dev build)

**What this closes.** `P0.5-B1` (§4y of `PHASE_CONTRACT.md`) is fixed in code (`789f741`) and unit-verified
(`tests/ipc_role_guard_test.cpp`, GREEN + RED). The one thing the unit test cannot cover is that the new Layer-2
role choke **does not break the genuine approval flow** — especially `brc100_auth_response`, which is on the money
path. This is that check. It is a **T3** (human at the machine) test.

It is a **two-sided invariant** (HARNESS §6): the same privileged IPC must **succeed from the approval overlay** and
be **refused from a self-navigated tab**. The two halves are each other's negative control — same message, opposite
role, opposite outcome. Neither half alone proves anything.

---

## ⛔ Isolation & money-safety (read first)

- **DEV build only.** Wallet **31401** (dev), frontend **5137**, browser launched with `HODOS_DEV=1`. **Never** touch
  prod wallet **31301**. **Never** run a prod-mode / installed bundle — it opens the real profile (standing rule).
  `mac_build_run.sh` / `win_build_run.*` set `HODOS_DEV=1`, so those launchers are the safe path; do not launch the
  built binary directly.
- **Grants are permission rows, not spends.** The attack half (Case B) writes/attempts a `/domain/permissions/*`
  row for a throwaway domain — **no funds move**. Clean it up after (or ignore it; it's the dev wallet).
- **The one money-path arm is `brc100_auth_response`** (it can approve a *spend*). In Case A do the approval on a
  **non-spend** prompt (a domain connect or a protocol "always allow") so **no UTXO moves**. If you specifically want
  to exercise a spend approval, do it on the **dev wallet only** with the **smallest** possible amount, and never on
  31301.

## Case A — the genuine approval flow still works (NO REGRESSION)

Goal: prove the choke lets the real approval overlay (role `notification` / `brc100auth`) through untouched.

1. In a tab, load a BRC-100 dApp (or the project's test dApp page) and trigger a wallet action that opens a real
   prompt — a **domain connect** (fires `add_domain_permission`) and, ideally, a **protocol/basket "Always allow"**
   prompt (fires `grant_scoped_permission`) and a **BRC-100 auth** (fires `brc100_auth_response`).
2. Click **Allow** / **Always allow** in the Hodos prompt (this prompt is the `notification`/`brc100auth` overlay).
3. **PASS criteria:**
   - The action completes as before (dApp connects / permission persists / auth proceeds).
   - The grant is written on the dev wallet — verify with the matching readback (dev port 31401):
     ```bash
     curl -s "http://127.0.0.1:31401/domain/permissions?domain=<the-dApp-domain>"            # trustLevel: approved
     curl -s "http://127.0.0.1:31401/domain/permissions/protocol?domain=<the-dApp-domain>"   # row present (scoped grant)
     ```
   - **In the log there is NO `🛡️ IPC DENIED (P0.5-B1 …)` line for that click.** (The choke saw the approval-overlay
     role and let it through.)
4. **If any P0.5-B1 denial fires here, STOP — the fix over-blocks the legit flow (a regression).** Most likely cause:
   the real approval overlay is running under a role other than `notification`/`brc100auth`. Capture the role from
   the log line and report it — do **not** widen `IsApprovalOverlayRole` without confirming that role is genuinely
   the approval overlay.

> Money note: the `brc100_auth_response` part of step 1 — prefer a **non-spend** auth/identity approval, or a
> protocol "always allow", so nothing broadcasts. Only exercise an actual payment approval if you specifically need
> to, dev wallet + minimal amount only.

## Case B — the self-nav attack is now REFUSED (THE FIX)

Goal: prove a self-navigated tab (role `tab_<id>`, internal origin) can no longer drive the family.

1. In a normal tab's **address bar**, type an internal BRC-100 approval URL and press enter — this navigates the
   **tab** to the internal route (role `tab_<id>`), which is exactly the attacker's self-nav state:
   ```
   http://127.0.0.1:5137/brc100-auth?type=protocol_permission&domain=attacker.example&kind=protocol&protocolName=probe&protocolLevel=2
   ```
   (This is the confirmed HIGH — `grant_scoped_permission`. The page renders the real "Always allow" prompt from
   these query params. For a param-exact replay, instead capture a genuine prompt's `window.location.search` from
   Case A via DevTools on the overlay and reuse it verbatim — the role is what differs, not the params.)
2. Click **"Always allow for this site"** (or **Allow**) on the rendered prompt.
3. **PASS criteria (the fix working):**
   - **The log shows** `🛡️ IPC DENIED (P0.5-B1 self-nav guard): 'grant_scoped_permission' from role 'tab_<id>'`.
   - **No grant row is written** for the attacker domain:
     ```bash
     curl -s "http://127.0.0.1:31401/domain/permissions/protocol?domain=attacker.example"   # expect: NO row / empty
     ```
4. **Repeat for the other family arms** by typing the matching internal URL / prompt type so each fires its IPC, and
   confirming each is denied + writes nothing:
   - `approve_cert_fields` — `…/brc100-auth?type=certificate_disclosure&domain=attacker.example&certType=probe&fields=firstName,lastName`
     → readback `curl -s "http://127.0.0.1:31401/domain/permissions/certificate?domain=attacker.example"` (empty).
   - `add_domain_permission` — a `type=domain_approval&domain=attacker.example` connect prompt → readback
     `curl -s "http://127.0.0.1:31401/domain/permissions?domain=attacker.example"` (not `approved`).
   - `approve_identity_key_reveal` / `approve_key_linkage_reveal` — the identity/linkage reveal prompts; deny logged.
   - `domain_permission_invalidate` — from the tab, attempt a revoke; expect
     `🛡️ IPC DENIED (P0.5-B1): domain_permission_invalidate from tab role 'tab_<id>'`.

> A/B is the negative control: in **A** the identical `grant_scoped_permission` (from the overlay) **writes** the row;
> in **B** (from a tab) it is **refused**. Same message, opposite role, opposite outcome — that is the two-sided
> proof. If B is denied but you never saw A succeed, the test hasn't shown the gate discriminates — do both.
